FINDING 1 - CROSS-USER ACCOUNT ACCESS
-------------------------------------

Severity reported by Strix: Medium
CWE: CWE-639
CVSS reported by Strix: 6.5

The ARIA query_account(user_id) tool accepts an arbitrary user identifier and
does not compare it with the authenticated session identity. An authenticated
customer can request another customer or staff record and receive profile,
balance, fraud-flag, and transaction information.

Evidence:

- agent.py:57-91 builds query_account without receiving current_user_id.
- agent.py:80-89 passes the caller-supplied user_id directly to database helpers.
- agent.py:103 builds tools without binding the authenticated user.
- database.py:93-111 correctly parameterizes SQL but performs no caller-level
  authorization check.

Root cause:

Authorization was delegated to the model prompt instead of being enforced in the
tool implementation.

Recommended remediation:

- Bind query_account to the server-side authenticated user.
- Reject a requested identifier that differs from the session principal.
- Enforce authorization before any database lookup.
- Add regression tests for cross-customer and staff-account access.


FINDING 2 - UNRESTRICTED INTERNAL POLICY ACCESS
-----------------------------------------------

Severity included in Strix's High combined tool-authorization report
CWE: CWE-862
CVSS reported by Strix for the combined report: 7.5

The lookup_policy tool accepts attacker-influenced topics and exposes every
knowledge-base entry without checking the authenticated user's role. The
internal_reference_only entry contains fictional restricted treasury, reserve,
borrowing, and fraud-override information.

Evidence:

- agent.py:64-77 returns any matching KNOWLEDGE_BASE entry.
- agent.py:68-69 advertises internal_reference_only as an available topic.
- knowledge_base.py:110-131 labels the entry confidential and restricts its
  intended distribution to Finance, Risk, and Compliance.

Root cause:

The model-facing tool has access to restricted content but no role-based policy
enforcement.

Recommended remediation:

- Classify policy topics by audience.
- Pass the authenticated role into the tool layer.
- Deny restricted topics before retrieving their contents.
- Return a generic access-denied response without revealing restricted topic
  names or content.
- Add customer-versus-staff authorization tests.


FINDING 3 - NAME-ONLY AUTHENTICATION
------------------------------------

Severity reported by Strix: Medium
CWE: CWE-287

The login form authenticates a user using only a full name. Anyone who knows or
guesses a seeded customer or staff name can impersonate that user and inherit the
corresponding session identity.

The UI separately checks that an OpenAI API key is valid. That does not prove
ownership of the NeoBank identity named in the form.

Evidence:

- app.py:390-404 and 451-478 use the entered name to establish NeoBank identity.
- database.py:127-137 authenticates by a case-insensitive name lookup alone.

Root cause:

A public identifier is treated as an authentication secret.

Recommended remediation:

- Use an established authentication provider or a verified secret/second factor.
- Do not use display names as credentials.
- Add failed-login, duplicate-name, staff-impersonation, and session-establishment
  tests.

Two public identifiers, such as a name plus a user ID, are not a genuine second
factor. Review raw AI-generated remediation advice before using it. No code fix
or successful post-fix retest is claimed by this recorded demonstration.


DEDUPLICATION NOTE
------------------

Strix displayed three vulnerability reports. Its High tool-authorization report
includes both the cross-user query_account path and internal-policy disclosure.
The Medium IDOR report separately describes the same query_account path.

For a professional final report, present three root-cause issues:

1. Cross-user account access
2. Unrestricted internal-policy access
3. Name-only authentication

Do not count the account-access evidence twice when calculating totals.

The raw severity and CVSS labels are scanner claims, not authoritative ratings.
Reassess their assumptions, including whether an authenticated user is needed.


USEFUL NEGATIVE RESULTS

- SQL injection was ruled out in the reviewed SQLite helpers because queries use
  bound parameters.
- No hardcoded API keys or credential-like secrets were identified in the
  sanitized target.
- Logout and API-key changes clear stored session identity, reducing identity
  reuse across turns.
- The exploitable authorization weakness resides in the agent/tool boundary,
  rather than SQL construction.

These are scoped observations from a quick source assessment, not proof that no
other vulnerability exists.
