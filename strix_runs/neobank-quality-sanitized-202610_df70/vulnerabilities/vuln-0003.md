# Name-only login allows account impersonation

**ID:** vuln-0003
**Severity:** MEDIUM
**Found:** 2026-10-29 10:22:30 UTC
**Target:** /workspace/neobank-quality-sanitized-20261028
**CWE:** CWE-287
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The login form authenticates NeoBank users by matching only the entered full name, so any known customer or staff name becomes a valid credential. An attacker who knows or guesses a real name can sign in as that person and inherit their session identity.

## Evidence

Local validation against an in-memory SQLite copy showed that a seeded full name immediately becomes the authenticated account:

```text
== login checks ==
Alex Mercer => ('USR-0042', 'Standard')
Morgan Hayes => ('USR-STAFF-01', 'Staff')
Not Real => None
```

The staff account is reachable with no secret beyond the name, so the session can be impersonated directly.

## Impact

A low-privileged attacker can impersonate another customer or a staff account with no password, token, or second factor. That lets the attacker act under the victim's identity in the workshop app and opens the door to any identity-bound actions the UI or tools expose to that session.

## Counterevidence

The app does verify the OpenAI API key before login, so the attacker needs a working key to reach the form. That check does not establish user identity, and it does not mitigate the fact that the bank account itself is authenticated solely by name.

## What Would Change This Severity

If login were changed to require a non-public secret bound to the account, the severity would drop; if the same name-only login were reachable without the API-key gate, the issue would become more severe.

## Technical Analysis

`app.py:393-490` asks only for a full name and then calls `authenticate_by_name(conn, name.strip())`. In `database.py:127-136`, `authenticate_by_name()` performs a case-insensitive lookup on `customers.name` and returns the matching row; no secret, second factor, or user ID is required. The result is that the first valid name entered becomes the authenticated session identity, including the staff account seeded in the workshop data.

## Proof of Concept

1. Open the login form and enter a seeded name such as `Morgan Hayes`.
2. Provide any OpenAI API key that passes the local workshop check.
3. Submit the form and observe that the app signs in as the matching account.
4. Repeat with a different valid name to impersonate a different customer or staff account.

```python
import sqlite3
from database import init_database, authenticate_by_name

conn = sqlite3.connect(':memory:')
conn.row_factory = sqlite3.Row
init_database(conn)

for name in ['Alex Mercer', 'Morgan Hayes', 'Adrian Cross']:
    customer = authenticate_by_name(conn, name)
    print(name, '=>', customer['user_id'], customer['tier'])
```

## Remediation

Require a second factor that is not publicly guessable, such as a user ID plus name, a one-time code, or another verified secret. Update the login form to collect the additional factor and switch the authentication call to a verifier that checks both fields before creating the session. Do not treat a display name as sufficient proof of identity.

## Fix Verification

Security closure: I validated the current login helper against an in-memory SQLite database and confirmed that the existing name-only path authenticates seeded staff and customer names without any secret. The proposed patch closes that boundary by requiring both a `user_id` and `name`, then using `authenticate_user()` so the session only opens when the pair matches.

Bypass review: I checked the only relevant alternate helper in the same module, `authenticate_by_name()`, and the patch stops routing the login form through it. A user who knows only the display name can no longer authenticate; a wrong `user_id` with a correct name fails as intended.

Preserved behavior: legitimate users can still sign in with the correct account identity, and the session values (`user_name`, `user_id`, `account_tier`) continue to populate exactly as before. The API-key verification and post-login session reset logic are unchanged.

Repository checks: `python3 -m py_compile app.py database.py agent.py` should be run on the scratch copy after applying the import and form changes. I also re-ran the in-memory SQLite helper validation to confirm the old name-only flow was exploitable and the new `authenticate_user()` predicate accepts only the matching pair. Gap: the scratch copy cannot import `langchain_openai` without installing the optional dependency, so I could not run the full Streamlit UI end-to-end.

## Assumptions

Assumes the seeded names are realistic targets for impersonation, which is true in the shipped workshop data because the app explicitly uses those names as login credentials.
