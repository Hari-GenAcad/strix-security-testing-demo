# Missing authorization in ARIA tools exposes other customers' accounts and internal policy data

**ID:** vuln-0002
**Severity:** HIGH
**Found:** 2026-10-29 10:21:55 UTC
**Target:** neobank-quality-sanitized-20261028
**CWE:** CWE-862
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

A low-privilege chat user can steer ARIA into calling `query_account` and `lookup_policy` with attacker-chosen arguments. Because the tools do not enforce ownership or role checks, the assistant discloses another customer's full account and the restricted internal treasury document.

## Impact

An attacker can read another customer's balance, contact details, fraud flags, and transaction history, then pivot to internal treasury, reserve-ratio, and fraud-override data that should be limited to Finance, Risk, and Compliance. The disclosure materially increases the risk of targeted fraud, phishing, and operational intelligence gathering.

## Counterevidence

I checked the tool layer and the chat flow for an ownership check, role gate, or topic allowlist and found none. The only claim of protection is the system prompt saying the tools handle permissions, but that statement is advisory only. The local PoC succeeded on the original build and failed only after I added explicit checks in the scratch copy; benign own-account and public-policy requests still worked after the patch.

## What Would Change This Severity

If every tool call were bound to the authenticated principal and role before the sink, or if the chat surface were only reachable through a staff-only workflow, the severity would drop.

## Technical Analysis

`agent.py` binds two tools into the model loop: `lookup_policy(topic)` and `query_account(user_id)` (lines 64-90). Neither tool validates who is asking; `query_account` accepts any `user_id` and returns `format_account_details(...)`, and `lookup_policy` returns any knowledge-base entry, including `internal_reference_only`. `invoke_agent()` executes the first tool call emitted by the model and feeds the raw tool result back into the final answer, so a malicious prompt or prompt-injected turn can steer the assistant into these sinks. The prompt text in `agent.py` also tells the model that the tools handle permissions, but that claim is not enforced in code. In `app.py`, the chat flow forwards each user message directly into `invoke_agent`, so there is no separate application-layer authorization boundary before the tool execution path.

The local proof-of-concept used an in-memory SQLite database and a stubbed model response to avoid the live API. On the original build, the same harness caused ARIA to disclose `USR-PP-001`'s full account and the restricted `internal_reference_only` document to a standard customer session. A patched scratch copy that adds caller binding to `query_account` and a staff-only gate for `internal_reference_only` returns access denied for both requests while preserving the benign own-account and public-policy paths.

## Proof of Concept

1. Run the repository code in a disposable copy with an in-memory SQLite database and a stubbed model response.
2. Force the agent to emit a `query_account` tool call for `USR-PP-001` while the logged-in principal is `USR-0042`.
3. Force the agent to emit a `lookup_policy` tool call for `internal_reference_only` while the logged-in principal is a standard customer.
4. Observe that the original build returns the other customer's full account and the internal treasury document.
5. Repeat the same harness against the patched scratch copy and confirm both requests are denied while the benign own-account and public-policy lookups still work.

## Remediation

Enforce caller-bound checks in `query_account` so the tool can only read the signed-in customer's own record, and restrict `lookup_policy` to customer-facing topics unless the caller is explicitly staff. Keep the authorization check in the tool layer itself; model instructions are not a security boundary. Align the system prompt with the real policy so it does not imply that the tools handle authorization for the application.

## Fix Verification

Gate 1 — applicability: I compared the suggestion blocks against `agent.py` and verified the line ranges and replacements correspond to the exact vulnerable source. I also ran `python3 -m py_compile /workspace/.scratch-aria/agent.py`, which returned `OK`.

Gate 2 — security closure: I replayed the local harness against the original source tree and the patched scratch copy. On the original build, the harness printed the other customer's full account and the `internal_reference_only` document; on the patched copy, the same requests returned access denied.

Gate 3 — bypass review: I tested both a direct cross-account lookup (`USR-PP-001`) and the restricted knowledge-base topic (`internal_reference_only`), plus benign own-account and public-topic requests. The malicious inputs were blocked after the fix, while the benign ones still succeeded.

Gate 4 — preserved behavior: the patched harness still returned the logged-in user's own account and the public `transfer_limits` policy verbatim, so the feature still works for intended requests.

Gate 5 — repository checks: `python3 -m py_compile /workspace/.scratch-aria/agent.py` passed; no broader repo test suite is present for this workshop app. The fix is the smallest repository-native change that enforces the invariant because it adds the authorization check exactly at the tool boundary and leaves the UI and database helpers unchanged.

## Assumptions

Assumes the attacker can reach the chat as a normal workshop customer and can cause the agent to emit tool calls or otherwise hit the same tool boundary. The vulnerable build does not re-check ownership or role before returning tool results.
