# Missing object-level authorization in ARIA `query_account`

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-10-29 10:20:37 UTC
**Target:** neobank-quality-sanitized-20261028
**CWE:** CWE-639
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The ARIA `query_account(user_id)` tool accepts a caller-supplied user ID and returns the matching account profile and transaction history without verifying that the requested record belongs to the logged-in user. Any authenticated customer can use the tool to read other customers' or staff records.

## Evidence

The shared validation note confirmed that `query_account` returned arbitrary records for `USR-PP-001` and `USR-STAFF-01`. The source path is equally direct: `agent.py:80-89` forwards the supplied identifier unchanged, and `database.py:93-111` performs a raw lookup by `user_id` with no ownership check.

```python
def query_account(user_id: str) -> str:
    logger.info(f"[TOOL] query_account('{user_id}')")
    customer = get_customer(conn, user_id.strip())
    ...
```

```python
def get_customer(conn: sqlite3.Connection, user_id: str) -> dict | None:
    row = conn.execute("SELECT * FROM customers WHERE user_id = ?", (user_id,)).fetchone()
```

## Impact

A logged-in attacker can disclose another person's balance, profile details, fraud flags, and transaction history, including staff accounts. That breaks account isolation and exposes sensitive banking data across user and role boundaries.

## Counterevidence

The only plausible safeguard is the authenticated user ID stored in Streamlit session state, but `query_account` does not consume it. I also checked the only `build_tools(...)` call site and found no alternate wrapper that re-binds the lookup to the session principal; the validation note showed the tool still returned customer and staff data when given mismatched IDs.

## What Would Change This Severity

If `query_account` were changed to compare the requested ID against the authenticated session user before any database read, the finding would be closed; if the tool were exposed without any login requirement, the severity would increase because the same lookup would become unauthenticated.

## Technical Analysis

`app.py` establishes a session user ID after login and passes it into `create_aria_agent(...)`, but `agent.py:80-89` ignores that trusted identity and forwards the user-controlled `user_id` directly into `database.py:93-111`. The database helpers are plain `SELECT ... WHERE user_id = ?` lookups with no caller-context check, so the tool can return any row whose identifier is known. The shared validation note confirmed the tool returns arbitrary customer and staff records after a successful login.

## Proof of Concept

1. Log in to the workshop app as any seeded customer.
2. Invoke the ARIA account lookup tool with a different known user ID, such as another customer or a staff account.
3. Observe that the tool returns the target's account details and transactions instead of rejecting the mismatched identifier.

```python
# After logging in as any customer, call the tool with a different user ID.
result = query_account("USR-STAFF-01")
print(result)
# Expected vulnerable behavior: the response contains the staff account details
# and transaction history instead of an access-denied error.
```

## Remediation

Bind account lookups to the server-side authenticated identity before any database read. Pass the current session user ID into the tool builder, reject any mismatched `user_id`, and add a regression test that confirms cross-user and staff IDs are denied even when the caller knows the identifier.
