│  Description                                                                │
│  The ARIA `query_account(user_id)` tool accepts a caller-supplied user ID   │
│  and returns the matching account profile and transaction history without   │
│  verifying that the requested record belongs to the logged-in user. Any     │

│                                                                             │
│  Impact                                                                     │
│  A logged-in attacker can disclose another person's balance, profile        │

│  user and role boundaries.                                                  │
│                                                                             │

│  `database.py:93-111`. The database helpers are plain `SELECT ... WHERE     │
│  user_id = ?` lookups with no caller-context check, so the tool can return  │
│  any row whose identifier is known. The shared validation note confirmed    │
│  the tool returns arbitrary customer and staff records after a successful   │
│  login.                                                                     │

│  Vulnerability Report                                                       │
│                                                                             │
│  Title: Missing authorization in ARIA tools exposes other customers'        │
│  accounts and internal policy data                                          │
│                                                                             │
│  Severity: HIGH                                                             │
│                                                                             │
│  CVSS Score: 7.5                                                            │
│                                                                             │
│  Target: neobank-quality-sanitized-20261028                                 │
│                                                                             │
│  CVSS Vector: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N                           │
│                                                                             │
│  Description                                                                │
│  A low-privilege chat user can steer ARIA into calling `query_account` and  │
│  `lookup_policy` with attacker-chosen arguments. Because the tools do not   │
│  enforce ownership or role checks, the assistant discloses another          │
│  customer's full account and the restricted internal treasury document.     │
│                                                                             │
│  Impact                                                                     │
│  An attacker can read another customer's balance, contact details, fraud    │
│  flags, and transaction history, then pivot to internal treasury,           │
│  reserve-ratio, and fraud-override data that should be limited to Finance,  │
│  Risk, and Compliance. The disclosure materially increases the risk of      │
│  targeted fraud, phishing, and operational intelligence gathering.          │
│                                                                             │
│  Technical Analysis                                                         │
│  `agent.py` binds two tools into the model loop: `lookup_policy(topic)`     │
│  and `query_account(user_id)` (lines 64-90). Neither tool validates who is  │
│  asking; `query_account` accepts any `user_id` and returns                  │
│  `format_account_details(...)`, and `lookup_policy` returns any             │
│  knowledge-base entry, including `internal_reference_only`.                 │
│  `invoke_agent()` executes the first tool call emitted by the model and     │
│  feeds the raw tool result back into the final answer, so a malicious       │
│  prompt or prompt-injected turn can steer the assistant into these sinks.   │
│  The prompt text in `agent.py` also tells the model that the tools handle   │
│  permissions, but that claim is not enforced in code. In `app.py`, the      │
│  chat flow forwards each user message directly into `invoke_agent`, so      │
│  there is no separate application-layer authorization boundary before the   │
│  tool execution path.                                                       │
│                                                                             │
│  The local proof-of-concept used an in-memory SQLite database and a         │
│  stubbed model response to avoid the live API. On the original build, the   │
│  same harness caused ARIA to disclose `USR-PP-001`'s full account and the   │
│  restricted `internal_reference_only` document to a standard customer       │
│  session. A patched scratch copy that adds caller binding to                │
│  `query_account` and a staff-only gate for `internal_reference_only`        │
│  returns access denied for both requests while preserving the benign        │
│  own-account and public-policy paths.                                       │
│                                                                             │

│  1. Run the repository code in a disposable copy with an in-memory SQLite   │

│  3. Force the agent to emit a `lookup_policy` tool call for                 │

│                                                                             │
│  # Executive Summary                                                        │
│                                                                             │
│  The workshop target exposes three meaningful weaknesses in the AI banking  │
│  flow. The highest-risk issue is the model/tool boundary: a normal chat     │
│  user can steer ARIA into disclosing another customer’s account data and    │
│  the restricted internal treasury policy document. A second issue lets an   │
│  attacker authenticate as any seeded customer or staff member using only a  │
│  public full name, and a third allows cross-user account reads through the  │
│  account lookup tool.                                                       │
│                                                                             │
│  Overall posture: elevated for a training target, with one high-severity    │
│  disclosure path and two medium-severity authentication / object-access     │
│  weaknesses. The SQLite query layer itself is not the problem; the exposed  │
│  authority sits in the agent/tool design and the name-only login flow.      │
│                                                                             │
│  # Methodology                                                              │
│                                                                             │
│  This was a source-aware white-box assessment of the local workshop         │
│  repository. The review combined static triage of `app.py`, `agent.py`,     │
│  `database.py`, `knowledge_base.py`, and `seed_data.py` with bounded        │
│  static analysis artifacts, in-memory SQLite validation, and stubbed model  │
│  responses so the live OpenAI API was not required. Validation focused on   │
│  prompt/tool abuse, internal-data disclosure, authentication strength,      │
│  object-level authorization, and SQLite/query handling, with negative       │
│  checks for SQL injection and session-reuse behavior.                       │
│                                                                             │
│  # Technical Analysis                                                       │
│                                                                             │
│  The core issue is that ARIA treats model instructions as if they were an   │
│  authorization boundary. In `agent.py`, the `lookup_policy` and             │
│  `query_account` tools accept attacker-influenced arguments with no         │
│  ownership or role checks, and the agent executes the first tool call       │
│  emitted by the model before reflecting the raw result back into the final  │
│  answer. That means a standard customer session can be steered to retrieve  │
│  another customer’s account or the internal-only treasury reference, which  │
│  materially increases the risk of targeted fraud and sensitive operational  │
│  disclosure.                                                                │
│                                                                             │
│  A separate authentication weakness exists in `app.py` and `database.py`:   │
│  the login form authenticates by full name only. Any seeded customer or     │
│  staff name becomes a valid credential, so an attacker who knows or         │
│  guesses a real name can sign in as that person and inherit the session     │
│  identity. The database helpers themselves use parameterized SQL and did    │
│  not show injection behavior, and the logout / API-key refresh path does    │
│  clear session identity state, so those areas were ruled out rather than    │
│  reported.                                                                  │
│                                                                             │
│  # Recommendations                                                          │
│                                                                             │
│  **Immediate**                                                              │
│  - Bind every account lookup to the server-side authenticated principal     │
│  before any database read.                                                  │
│  - Restrict internal policy topics to staff-only sessions and return        │
│  access-denied errors for standard users.                                   │
│  - Replace name-only login with a real second factor or a verified account  │
│  secret.                                                                    │
│                                                                             │
│  **Short-term**                                                             │
│  - Add regression tests for cross-user account reads, staff-account         │
│  access, and restricted policy disclosure.                                  │
│  - Align the system prompt with the real authorization model so it does     │
│  not imply the tools enforce security.                                      │
│                                                                             │
│  **Medium-term**                                                            │
│  - Add a narrow authorization layer around all model-facing tools, not      │
│  just `query_account`.                                                      │
